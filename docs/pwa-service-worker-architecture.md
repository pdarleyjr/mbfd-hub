# ADR: PWA and service-worker architecture (Option C on B's mechanics)

- Status: Accepted, Phases 1 and 2 implemented on `feat/workflow-notifications-pwa`
- Date: 2026-10-23
- Scope: `public/sw.js`, `public/admin-pwa/service-worker.js`, `resources/js/daily-checkout/public/service-worker.js` (built to `/daily/sw.js` and `/daily/service-worker.js`), `resources/js/pwa/*`, `resources/js/daily-checkout/src/pwa/*`, `GET /app-release`
- Related: `2.AI_AGENT_ERRORS.md` ERROR-037 (dual registration reload loop), `docs/NOTIFICATIONS_PLAYBOOK.md`, `docs/PUSH_NOTIFICATION_DIAGNOSTIC.md`

## 1. Context

### 1.1 What is registered today

A registration is keyed by (origin, scope). Installed devices only ever look for updates at the exact script URL they registered, so every URL below is frozen.

| Id | Script URL | Scope | Source in repo | Registered by | Job |
|---|---|---|---|---|---|
| R1 | `/sw.js` | `/` | `public/sw.js` (hand-written, committed) | `resources/js/push-notification-widget.js`, only on the two settings pages (`/admin/settings`, `/training/settings`) | Push display and notification click. No `fetch` handler. |
| R2 | `/admin/service-worker.js` (a Laravel route that serves `public/admin-pwa/service-worker.js` with `Service-Worker-Allowed: /admin/`) | `/admin/` | `public/admin-pwa/service-worker.js` | `resources/js/admin-pwa/main.ts`, every `/admin/*` page | Static-asset cache plus push. Never caches authenticated HTML or JSON. |
| R3 | `/daily/sw.js` | `/daily/` | `resources/js/daily-checkout/public/service-worker.js` template, generated by the Daily Vite build | `resources/js/daily-checkout/src/main.tsx` | Daily Checkout offline shell and API cache, plus push handlers. |

Other URLs that may still be registered on old devices and must keep answering with a working worker: `/admin-pwa/service-worker.js` (legacy alias), `/daily/service-worker.js` (build byproduct), and `?v=` variants of `/daily/sw.js` and `/admin/service-worker.js`.

Manifests: one linked manifest, `/manifest.json` (`id "/"`, `start_url "/"`, `scope "/"`). `/admin-pwa/manifest.webmanifest` and `/daily/manifest.*` exist but nothing links them. Devices can carry four historical installed identities (root `/admin`, Admin `/admin/?source=pwa`, Daily `/daily/`, root `/`). Manifest `id`, `start_url` and `scope` are frozen.

Nesting: the longest scope prefix controls a page. `/daily/*` is R3, `/admin/*` is R2 once registered, everything else is R1 if present.

### 1.2 What was wrong

1. Push display and `notificationclick` existed three times and disagreed (permission gate, payload parsing, `requireInteraction`, icon, default tag, which window to reuse).
2. R1 and R3 returned early when `Notification.permission` was not `granted` and called `event.data.json()` unguarded. Safari and iOS revoke a subscription that receives a push without a visible notification, so a garbled or empty payload could silently cost a member their notifications.
3. Click handlers called `WindowClient.navigate()`. Safari throws `NotSupportedError`, and Chromium rejects it for a window controlled by a different registration, so the deep link was dropped. It also navigated away from a window where the member might have unsaved work.
4. No release identity reachable by a worker or a logged-out page (`/__version` is auth-only). The edge cached `/sw.js` for four hours.
5. Update behavior differed per worker: an admin toast that only desktop saw, nothing for R1, nothing for Daily. Daily has no chunk-load recovery after a deploy.

### 1.3 Hard constraints (release blocking)

Nobody may be forced to reinstall, clear site data or lose a push subscription. Therefore: no change to worker script URLs or scopes, no change to manifest `id`/`start_url`/`scope`, no VAPID change, no change to the `push_subscriptions` schema, no `unregister()`, no IndexedDB deletion, and no second registration of any worker URL.

## 2. Options

| | A. One unified worker | B. Scoped workers sharing compiled code | C. B plus central page-side orchestration |
|---|---|---|---|
| Idea | Replace R1/R2/R3 with one worker at `/`. | Keep R1/R2/R3 at their URLs and scopes. Compile one shared core (push, click, subscription refresh, message protocol) into each. | B, plus one page-side registrar for release detection, update prompts, chunk recovery and notification routing. |
| Registrations | Cannot replace R2/R3: nested scopes always win, so they stay unless unregistered. | Unchanged. | Unchanged. |
| Push subscriptions | Removing R2 destroys the subscriptions bound to it (they live on the registration, and the database cannot say which registration a row belongs to). | Untouched. | Untouched. |
| Risk | A `fetch` handler in front of Livewire, login and password flows (the admin worker header records a Cancel-destination incident from exactly that). | Low. | Low. Adds page code, which is additive and feature-detected. |
| Fixes duplication | Yes | Yes | Yes |
| Fixes update UX and release skew | Partly | No | Yes |
| Verdict | Rejected | Necessary, incomplete | Chosen |

## 3. Decision

Adopt Option C, implemented with B's mechanics: one shared worker core inlined at build time into each worker script at its existing URL, one page-side registrar shared by every Hub surface, and a public release-identity endpoint. Specialized offline behavior stays where it lives (Daily only). Offline data (Dexie `mbfd-daily-checkout`, `mbfd-operational-forms`, `mbfd-admin-cache`, localStorage drafts) is origin-scoped, owned by no worker, and is not touched.

## 4. Phase 1: what ships

### 4.1 Worker core (`resources/js/pwa/worker-core.js`)

Classic-script safe (no module syntax, no `importScripts`). Version constant `MBFD_WORKER_CORE_VERSION`. Each worker also declares `MBFD_WORKER_BUILD_ID` (root: `mbfd-root-push-<date>.<n>`, admin: its `VERSION`).

- `push`: always calls `showNotification` inside `event.waitUntil`, with no early return and no permission check. Parses the current app payload (`{title, body, icon, badge, tag, data:{url}, actions, requireInteraction}`), Declarative Web Push (`{web_push: 8030, notification: {title, body, navigate, tag, ...}}`) and plain text. Empty, garbled or wrongly typed payloads render with defaults. If the full option set is rejected it retries with a minimal set so the push is still visible. Icons must be same-origin. Without a tag it derives one from the content, so the same alert delivered through two registrations collapses while different alerts stack.
- `notificationclick`: closes the notification and resolves the destination with the original same-origin rule (anything cross-origin or malformed becomes `/`). Then, in order: (a) a window already showing exactly that path and query is focused; (b) otherwise the best same-origin window (focused, then visible) is focused and receives `{type:'MBFD_NAVIGATE', url}` with a `MessagePort` for an acknowledgement, so the page decides; (c) otherwise `clients.openWindow`. If the chosen page never acknowledges (a Hub surface that does not load the registrar, or a page still running old JavaScript), the worker opens a window rather than silently dropping the deep link. The acknowledgement wait is a 600 ms total budget that starts when the page is asked, before `focus()` has settled, and focusing runs alongside it: Firefox and WebKit only allow `openWindow` for about a second after the click, and a slow `focus()` used to push it past that (core `2026-10-23.2`). `WindowClient.navigate()` is never used. Action buttons may carry their own destination; `dismiss` and `close` actions only close.
- `pushsubscriptionchange`: best effort. Uses the browser-provided `newSubscription`, or re-subscribes with the old `applicationServerKey`, then `POST /api/push-subscriptions` with credentials (and `X-XSRF-TOKEN` from `cookieStore` where the browser has it). Never throws.
- `message`: `{type:'SKIP_WAITING'}` calls `skipWaiting()`; `{type:'GET_VERSION'}` replies on `ports[0]` with `{type:'MBFD_VERSION', build, core}`.

Behavior differences members may notice: root and admin workers now behave identically (sticky `requireInteraction` by default as R1/R3 did, unless the payload says otherwise; the badge/icon default to `/images/mbfd-logo.png`, which is what every server sender already specifies).

### 4.2 Build-time inlining

`scripts/pwa/build-service-workers.mjs` rewrites the text between `/* MBFD_WORKER_CORE:START */` and `/* MBFD_WORKER_CORE:END */` in `public/sw.js`, `public/admin-pwa/service-worker.js` and (Phase 2) the Daily template `resources/js/daily-checkout/public/service-worker.js`. Output is committed, deterministic and idempotent. `--check` (also `npm run check:service-workers`) fails on drift; `tests/Node/pwa-worker-core.test.mjs` runs that check, and CI already executes `node --test tests/Node/*.test.mjs` in `06-static-analysis.yml`. Workflow: edit the core, run `npm run build:service-workers`, commit both.

Worker specifics kept intact:

- `public/sw.js`: install `skipWaiting`, activate `clients.claim`, still no `fetch` handler (taking control is harmless). The unused `CACHE_NAME` was dropped; nothing read it.
- `public/admin-pwa/service-worker.js`: caching strategy, bypass list, unproxied navigations and the `mbfd-admin-*` cache cleanup are unchanged. `VERSION` is `mbfd-admin-v4`, which makes the file byte-different so installed devices update it in place and drop the v3 cache.

### 4.3 Release identity

`App\Support\Release\DeployedRelease` answers two questions. `commit()` is the deploy proof (private `deploy-marker.json`, then `.git-sha`, then `unknown`) and is what `AddBuildHeaders` sends as `X-App-Commit` (unchanged behavior, still pinned by `AddBuildHeadersTest`; the deploy smoke checks compare it with the marker). `servedCommit()` and `short()` name the build that is actually serving the page: the image's `.git-sha` first, then the marker, then `unknown`. The marker lives on a host bind mount and is written only after the new container is up and smoke-tested, so for the whole deploy window (and after a rollback or a failed marker step) it still names the previous release; the page-facing identity must not. `GET /app-release` returns `{"release":"<first 12 chars of servedCommit>"}` with `Cache-Control: no-store`, `throttle:600,1` per address (stations share one egress address and every device probes on return and on `online`), no session start, no cookie, and none of the member-state redirects. `<meta name="mbfd-release">` is added to `components/hub/head.blade.php`, which both standalone views and every Filament panel (except policy-library) render. Only 12 characters of the commit are exposed.

### 4.4 Page side (`resources/js/pwa/`)

- `busy.ts`: a single `window.__mbfdBusy` set shared by independent bundles. `markBusy(reason)`, `clearBusy(reason)`, `isBusy()`, `onBusyChange()`. Reasons: `unsaved-draft`, `queued-submission`, `active-call`. A `hasUnsavedFieldEdits()` safety net treats typed-but-unsaved text, ticks and selections as busy even where no feature called `markBusy` (search boxes excluded), so the Hub is safe before every form is wired. Ordinary controls are compared with their server-rendered defaults at decision time (stateless). Edits the DOM cannot reveal are recorded by `startFieldEditTracking()` (started by the registrar): a capturing, trusted-only `input`/`change` listener on the document remembers the contenteditable surface (Trix, Filament's rich editor), role=textbox surface, hidden mirror input or file input the member edited, as a per-page set of elements. The set heals itself (an element that left the page, or a file input that was emptied, stops counting) and is cleared when a Livewire action (not a `$refresh`/poll) succeeds, on `livewire:navigated`, and when a non-prevented form submit hands the page to the browser. Search areas and `[data-mbfd-ignore-edits]` are ignored. Scripts' synthetic events (`isTrusted` false, such as Trix mirroring into its hidden input) never count.
- `update-registrar.ts`: one instance per page (first caller wins; later bundles add their scope). Baseline from the meta tag, else the first `/app-release` answer. Checks (no-store) on visible, online, `pageshow` from bfcache and every ~30 minutes with jitter. On a new release it calls `registration.update()` for its own scope and shows the banner. Reload policy: at most one automatic reload per release, only when not busy and the tab is hidden, guarded by `sessionStorage` key `mbfd-reloaded-for:<release>`; if storage is unusable, automatic reloads are off. The banner's "Refresh now" is a user action and works unless the page is busy (it is `aria-disabled` while busy). No `controllerchange` listener causes a reload. `vite:preloadError` is handled (`preventDefault`) by the rules in `chunk-recovery.ts`: a reload (once per release, only when free) needs positive evidence the network is up (the release probe answered) and a reason it will help (a different release is live, or the failed file, named in the error, answers 404/410 to a `HEAD`); a failed probe never reloads and shows "You're offline. Some screens will load when you're back online." instead (cleared by the next successful probe); a reachable server, same release and a chunk that is not missing (a blip, or a browser that names no file) shows the manual "Refresh now" banner. `MBFD_NAVIGATE` is validated same-origin, acknowledged, and either followed with `location.assign` or deferred behind an "Open notification" link.
- Wiring: `resources/js/hub-shell.js` (every Hub shell page and every Filament panel except policy-library) starts it with scope `/`; `resources/js/admin-pwa/main.ts` starts it with scope `/admin/` after its single existing registration. Neither passes `scriptUrl`. The old desktop-only admin toast was removed because the registrar replaces it on all platforms.

The registrar never registers `/sw.js` on Hub pages. It only attaches to a root registration the device already has (created by the push settings page). Registering it everywhere was rejected: it would add a worker to every device that has not opted into push for no member benefit, and it is not needed for notification routing because `clients.matchAll({includeUncontrolled:true})` reaches uncontrolled windows. If a future need arises, the exact call is `navigator.serviceWorker.register('/sw.js', { scope: '/' })`, identical to the widget's (a no-op when already registered).

## 5. Migration and safety plan

- No worker is unregistered and no cache or database is deleted by new code (the admin worker deletes only its own older `mbfd-admin-*` caches, as before).
- Script URLs and scopes are untouched, so each installed registration updates in place from its own URL. This was exercised against the exact pre-change production bytes (section 8).
- Push subscriptions stay on the registration that owns them. R1 subscribers and R2 subscribers both keep working because both workers ship the same handler.
- VAPID keys, the `push_subscriptions` schema and the server senders are unchanged.
- Duplicate registration is structurally avoided: the registrar registers only if a caller passes `scriptUrl` and no registration exists, and nobody does today. No `?v=` anywhere (ERROR-037).
- New subscriptions bind explicitly to the root registration (`/sw.js`, scope `/`, `updateViaCache: 'none'`, identical to the push widget and the admin page) instead of `navigator.serviceWorker.ready`, which on `/admin/settings` resolves to R2. Done naively that would show existing R2/R3 subscribers as "not subscribed" and create duplicates, so `resources/js/pwa/push-enrollment.ts` inspects ALL registrations (`getRegistrations()` plus the root one, collapsed by endpoint): a subscription found anywhere means the device is enrolled and it is synced to the server instead of creating a new one, "Turn on" with a usable subscription elsewhere creates nothing, subscriptions made with another server key are removed, and "Turn off on this device" unsubscribes every subscription on the device and deletes each one server-side. Still open from that plan: a write-only diagnostic of the registration scope per subscription.
- Edge freshness: `server.php` makes `/sw.js` and `/admin-pwa/service-worker.js` revalidate (`no-cache, must-revalidate`). `/admin/service-worker.js` is already served by Laravel. `/admin-pwa/service-worker.js` is a real file, so `server.php` also sends `Service-Worker-Allowed: /admin/` for it (the Laravel route that adds the header is never reached); without it a device whose `/admin/` registration came from that legacy URL cannot validate its own updates.

## 6. Rollback

The core is additive. Reverting the commit restores the previous worker bytes at the same URLs; devices update in place on their next check (edge no-cache, `updateViaCache: 'none'`). The admin worker's cleanup then removes the v4 cache and the old worker recreates v3. Pages without the registrar are harmless: a worker's `MBFD_NAVIGATE` is acknowledged only by pages that have it, otherwise the worker opens a window. `/app-release` and the meta tag are inert without the registrar. No data migration exists to undo. Phase 2 adds one rollback fact: a Daily worker replaced by the previous production bytes (v10 or v11) deletes the v12 cache names on activation (its own cleanup removes every other `mbfd-checkout-*` and `mbfd-api-cache-*` name), keeps working with the same drafts and queue, and its caches refill from the network; this is exercised against the exact live bytes in `tests/e2e/daily-checkout-sw-upgrade.spec.ts`.

## 7. Phase 2: Daily Checkout on the shared core and update system

Phase 2 brings the Daily worker (R3, `/daily/sw.js`, scope `/daily/`) and the Daily app onto the same push core and update protocol as every other surface. Nothing in section 1.3 moves: the worker URL, scope, manifest and VAPID are unchanged, the page still performs one plain `register('/daily/sw.js', { scope: '/daily/' })`, nothing is unregistered, and no IndexedDB database is opened, changed or deleted by any new code.

### 7.1 Shared core inlined into the Daily worker

`resources/js/daily-checkout/public/service-worker.js` (the template the Daily Vite build turns into `/daily/sw.js`) carries the generated core between the same `MBFD_WORKER_CORE` markers. `scripts/pwa/build-service-workers.mjs` (and its `--check`, `npm run check:service-workers`, and `tests/Node/pwa-worker-core.test.mjs`) now cover three targets. The Daily Vite plugin refuses to build a template that lacks the core.

- The Daily worker's own `push`/`notificationclick` handlers (permission gate, unguarded `event.data.json()`, `client.navigate()`) are gone. Pushes always show a notification; a click focuses the best Hub window and asks the page to navigate (`MBFD_NAVIGATE`), which the Daily page now answers.
- `message`: the core answers `SKIP_WAITING` and `GET_VERSION` (build id is the cache name, `mbfd-checkout-v12`). The Daily handler keeps `QUEUE_SUBMISSION` and `SYNC_QUEUE` (unchanged replies) and adds `PURGE_USER_CACHES`; it no longer handles `SKIP_WAITING`, so one message is never processed twice (tested).
- `/app-release` is never intercepted by the worker (the registrar's probe must not be cached).

### 7.2 Cache contract change (`mbfd-checkout-v12`, `mbfd-api-cache-v8`)

The old worker stored every OK GET under `/api/public/stations*` and `/api/public/apparatuses*` in one URL-keyed cache for every member that ever used the device (and kept a per-member `/daily/index.html` shell), with no purge on logout or user switch. The checklist response alone carries member-specific data (`pendingCorrections[].mine`), and station request, activity and equipment-request responses are member data. Changes:

1. Only an explicit allowlist is cached: every station-wide read the Daily screens make (audited against `utils/api.ts`, and pinned by a test that re-derives the list from that file): the apparatus list, an apparatus checklist, the station list, station detail, rooms, room assets, room profile, a station's apparatus, inspection history, gas meters, equipment requests, requests (any query string) and activity. This is the set the baseline (fc35bb83) cached by prefix; the first Phase 2 cut had narrowed it and broke offline station inspections, gas meters and room profiles. Requests, equipment requests and activity are station-scoped with requester identity redacted (`PublicStationRequestResource`), so they are not member-private; the genuinely member-specific response (a checklist carries the viewer's pending corrections) is why every API cache is purged on sign-out and user switch, which covers all of them equally. Service tickets and notices stay live (`no-store`), as in the baseline. Everything else under `/api/` always goes to the network with `no-store`. Offline, an uncached allowlisted read model answers a JSON 503 as before.
2. `mbfd-checkout-v12` and `mbfd-api-cache-v8` replace v11 and v7. Activation deletes the old names, which is a one-time purge of whatever earlier members left behind. Devices keep working in between: the old worker keeps serving until the new one activates. Before the older cache is deleted, activation copies its `/daily/assets/*` into the new cache (the newest older cache only, at most its newest 300 entries, complete 200 responses only), so a tab still running the previous JavaScript (an installed app stays resident for days) can lazy-load its chunks instead of getting a 404 from the new release. The cache name stays the same across later releases, so activation also keeps a record (`/__mbfd/daily-asset-generations`, never requested by a page) of the current and the previous release's asset list and deletes `/daily/assets/*` older than those two; a build without an asset list never prunes. This also ends the unbounded accumulation of old hashed assets. `CACHE_NAME` was not bumped (v12 has not shipped).
3. `{type: 'PURGE_USER_CACHES'}` (same-origin pages only) deletes every `mbfd-api-cache-*` cache, replies `{type: 'USER_CACHES_PURGED', success}` on the supplied port as soon as that is done, and then refreshes the member's Daily shell fetch-first from `/daily/` (the Laravel-rendered shell with its release meta tag, never the raw static `/daily/index.html`, stored under both keys): a genuine shell replaces the stored one; proof the session is gone (a 401, or a redirect that ended on the sign-in page) removes it; anything else (offline, a flaky network, a 5xx, a 403, a redirect to the canonical host, forced password change or city e-mail review) leaves the stored shell alone, so an offline launch is never lost to a purge. When a genuine shell came back the session is proven, and the worker fetches again, one at a time and bounded to 10 requests (`/api/public` is throttled to 60 a minute per member), the two lists plus the read models the purged caches held, most recent first, storing only complete JSON answers: the offline checkout is not left empty after a user switch. A sign-out re-fetches nothing. A purge also bumps an epoch: a read, a shell or a re-fetch that was already in flight, or whose write was in progress, cannot be stored afterwards. It touches Cache Storage only.
4. The worker also checks by itself when a `/daily/` navigation is answered with a redirect: the browser hides where it leads, so it asks again with redirects followed and purges only if that ends on the sign-in page (or answers 401), so a logout elsewhere in the Hub is cleaned up the next time Daily is opened online, even though no Daily JavaScript ran, while a redirect to the canonical host, forced password change or city e-mail review keeps everything.

Page side (`resources/js/daily-checkout/src/pwa/userCaches.ts`): after `/api/me/context` confirms the member (`refreshOfflineIdentity`), `noteAuthenticatedUser(id)` compares a marker in `localStorage` (`mbfd-daily-device-marker`: a random salt plus a SHA-256 digest of salt and id; an FNV hash is the only fallback on an insecure context) with the previous one. The marker never contains the id, a name or any other personal data; it is not a secret (member ids are small integers), it only keeps the id out of storage in the clear. The first sighting only records the marker and purges nothing: it happens exactly once per upgraded device, right after the member's first online visit stored the apparatus list and checklists, so purging then would delete what that visit just stored and leave the offline checkout empty; and nothing needs protecting, because the previous worker's API cache was deleted when this worker activated. (Residual: a page still running pre-upgrade JavaScript can store a previous member's reads in the new cache before this code ever runs on that device, and a different member's first sighting will not purge them. They are station-scoped read models and a checklist with the old member's own pending corrections, they are removed by the next user switch, sign-out or worker upgrade, and a shared station tablet that has already passed through one new-code sign-in is covered.) A different member sends the purge message first and records the new marker only after the purge succeeded (a failure is retried on the next check). If no worker answers within 4 s (none installed yet, or an older worker that does not know the message) the page removes the API caches itself through its own `CacheStorage` handle; it leaves the shell to the worker, because replacing it needs the network. A 401 from `/api/me/context` or any `redirectToLoginAfterSessionExpiry()` purges once per signed-out episode, and the message is posted synchronously so it survives the redirect. Drafts and queued submissions stay in IndexedDB, owner-bound by their own records, exactly as before (verified: they survive a user switch and a lapsed session untouched, and a different member never sends them).

Residual risk, unchanged by design: if a member signs out through the Hub and the device then goes offline before Daily is opened online, the previous member's cache is still on the device. Nothing in the browser can observe that. The queue and drafts are owner-bound; the cached lists are removed at the first online use.

### 7.3 `/daily/service-worker.js`

Decision: keep the URL, make it byte-identical to the built `/daily/sw.js`. The audit found nothing in the repo registering it, but an installed device from the 2026-01 to 2026-03 era may still check that URL, and `server.php` serves it with `no-cache`. Returning 404 would make Chromium drop that registration, and returning the raw template (an empty precache list) would install a worker that claims the same caches with no assets. The Vite plugin overwrites the publicDir copy with the built worker, so both URLs always ship the same bytes, with the same scope rules (the script directory, `/daily/`). Tested: the two build outputs are equal, and a page that registers `/daily/service-worker.js` gets the full worker with its precache list and `GET_VERSION` answer.

### 7.4 Page side in Daily

- `main.tsx` keeps its single registration and adds `startUpdateRegistrar({ scope: '/daily/' })` (no `scriptUrl`): release detection, the update banner (the registrar's own, 44 px targets), chunk-load recovery (`vite:preloadError`) and the `MBFD_NAVIGATE` listener. The Laravel route that renders the Daily shell now writes `<meta name="mbfd-release">` (same value as `/app-release`), so a shell restored from the offline cache after days is recognised as old instead of being taken for the current release. The Vite preview used by the Daily e2e suite answers `/app-release` with a constant.
- Busy reasons (`resources/js/daily-checkout/src/pwa`, one registry shared with the other bundles):
  - `unsaved-draft` is held while any source holds unsaved work, and only while: the inspection autosaver has edits not yet confirmed in IndexedDB (a failed write stays busy; unmounting releases it), the 300 Command composer has text or files (it is memory-only by design), or an ordinary in-memory form has typed text (React keeps the `value` attribute in step, so the registrar's own field check cannot see these). The form watcher releases itself when the field is cleared, disabled or removed, ignores search and filter boxes, the inspection wizard and `[data-mbfd-ignore-edits]`.
  - `queued-submission` is held while the Daily queue or the generic form queue has records that will still be sent. Records parked for a decision (`requires_attention`) are excluded so they can never pin the page busy. A count that cannot be read (or hangs) is treated as busy and retried; only three failures in a row (IndexedDB evidently unavailable, so no queue exists) release the page.
- The registrar itself gained fixes found while testing a device that wakes up after days offline: after activating a worker it re-checks that the page is still free (busy, and for an automatic reload also typed fields) and abandons (and un-guards) the reload if work started meanwhile; a failed probe no longer counts as a check for the rate limit; the browser coming back online always checks; and a worker update that failed (network drop, precache failure) is retried on the next check instead of being forgotten.

### 7.5 Video conferencing

`ConferenceApp.tsx` marks `active-call` while connected or reconnecting (keyed on the boolean so connected to reconnecting never flashes idle) and clears it on leave, end and unmount. The standalone conferencing page does not load a Hub bundle, so no registrar is mounted there; the flag is set through the shared window-global registry so the Filament employee page (which loads `hub-shell.js` and therefore the registrar) honours it. The mount chunk stays inside its budget (checked by `npm run test:video-conferencing-bundle`).

### 7.6 Still open

1. Wire `unsaved-draft` from Operational Forms drafts (`resources/js/operational-forms`) and from the take-home inspection's pending photo uploads and signature canvas (photos held in script state after the file input was reset are invisible to the generic file-input tracking in 4.4).
2. Add `npm run test:pwa-update-e2e` and `npm run test:daily-pwa-upgrade-e2e` to a CI job, and `/sw.js` plus `/daily/sw.js` freshness checks to `production-activate.yml`.
3. A write-only diagnostic of the registration scope per push subscription (the dual-registration lookup itself shipped, section 5).

## 8. Verification

## 9. Guided recovery for unavoidable browser limits

Some situations cannot be fixed by code because the browser, not the app, removed the subscription or the permission. In every case the member can recover without a developer, and nothing else in the Hub is affected.

| Situation | Why it happens | What the member does |
|---|---|---|
| iPhone or iPad: the Home Screen app was deleted and added again | A re-added Home Screen app is a new identity with its own permission and subscription. | Open the Hub app, go to Settings, tap Enable Push Notifications and allow. The old subscription expires on the server when the push service reports it gone. |
| iOS or Safari revoked notifications | Safari revokes a subscription that received a push without a visible notification, or the member switched notifications off in iOS Settings. | Turn notifications back on in iOS Settings for the Hub app if they were switched off, then Settings in the Hub, Enable Push Notifications. A user tap is required on iOS. |
| Site data cleared, "Clear browsing data", or Safari's seven-day cleanup for non-installed use | The registration and its subscription are deleted with the site data. | Open the Hub and enable push again from Settings. Installing to the Home Screen avoids the seven-day cleanup. |
| Chrome or Edge removed the notification permission automatically | Chromium removes it for sites with low engagement and high notification volume (installed apps are exempt). | In the browser's site settings set Notifications to Allow, then enable push in Hub Settings. |
| Lockdown Mode (iOS or macOS) | Service workers are disabled. | Push is unavailable in that mode; the Hub itself still works. |
| A pushed link does nothing or opens the home page | The notification's destination was cross-origin or malformed and the worker deliberately fell back to `/`. | Open the item from the Hub. Report to Hub support so the sender can be corrected. |

Support checklist for "I stopped getting notifications": confirm the app is installed to the Home Screen on iOS; Settings in the Hub shows "Enable Push Notifications" (not subscribed) or the subscribed state; send a test notification from the same screen; if the button is missing, the browser lacks push support or the page is not running as an installed app.

## 10. Limits and open items

- Real push delivery, a real notification tap on a device, Safari/iOS behavior, and WebKit's silent-push tolerance are not testable in CI.
- Chromium automation here cannot create a push subscription (`AbortError: Registration failed - permission denied`), so survival of a live subscription across the worker update is argued from the Push API (a subscription belongs to the registration, and the registration object was verified to persist) rather than observed.
- `requireInteraction` defaults to sticky for everyone, matching R1/R3. A payload that sets it explicitly is honored (the current server senders do not set it).
- A page that is hidden for days on iOS may sit on an old release. The registrar checks on every return to visible, which is the earliest the platform allows.
- Phase 2 was tested in Chromium only. WebKit and iOS (including the Home Screen app and `postMessage` to a worker from a page outside its scope) and Firefox are not covered; the code uses only `MessageChannel`, Cache Storage and `localStorage`, all available there.
- API cache keys include the query string, so variants of an allowlisted URL accumulate until the next purge or worker upgrade, and an offline lookup for a variant that was never fetched answers the JSON 503.
- Known and not changed in the review follow-ups: a 5xx answer to a `/daily/` navigation during the deploy's force-recreate window is shown instead of the stored shell (pre-existing); `pushsubscriptionchange` re-POSTs without a CSRF token in browsers that have no `cookieStore` (Firefox, Safari), so there it can fail silently and the settings page re-syncs on the next visit (the route stays CSRF-protected; also pre-existing, best effort by design).
- A member who signs out through the Hub and then goes offline before Daily is opened online keeps the previous member's cached lists until the first online use (7.2). The queue and drafts are owner-bound.
- Operational Forms drafts do not report `unsaved-draft` yet; the registrar's stateless field check still protects ordinary form controls there.
