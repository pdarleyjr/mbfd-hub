# MBFD Hub — Design System

Design authority: the approved Opus 5.5 modernization and the implemented Hub tokens.

## Product and audience

**Operational clarity on a white field.** MBFD Hub serves firefighters, station personnel,
officers, administrators, workgroups, and training staff. Home, Daily Checkout, Employee,
Admin, Workgroups, and Training must feel like one dependable municipal application.
Prioritize recognizable destinations, useful data density, clear status, and fast recovery.
Known information should be entered once and reused. Preserve existing authorization and
operational behavior when improving presentation.

## Identity and color

- Use a crisp white page canvas, a compact navy authority bar, and blue primary actions.
- Reserve red for the departmental mark, confirmed live incidents, critical states, and
  destructive actions. Ordinary navigation and primary actions use blue.
- Use 1px cool-neutral borders and spacing for hierarchy. Keep shadows restrained; overlays
  may use the existing elevation tokens. Cards do not need decorative gradients or lift.
- Retain the real MBFD mark. Domain accents identify modules; they do not replace action
  colors or semantic statuses.

`resources/css/hub-components.css` owns the scoped `--hub2-*` tokens under
`[data-hub-ui="2"]`. Consume these tokens and the existing shared brand variables; do not
scatter new hex colors across views. Filament uses matching supported panel color
configuration. Daily uses the same brand and cool-neutral values.

for secondary text, and `n-500` for muted text. Lighter tokens are surfaces and borders,
not ordinary text. Warm stone palettes and red primary CTAs are superseded.

## Typography

Plus Jakarta Sans is the primary family for headings, body text, labels, and controls.
Use self-hosted `@fontsource-variable/plus-jakarta-sans` assets and the configured Filament
font provider. Keep system fallbacks for loading and offline resilience; do not fetch
Google Fonts at runtime. Headings and strong labels use 600–700 weight; body text uses
400–500. Numeric data uses `font-variant-numeric: tabular-nums`. Use the existing system
monospace token only when code or an identifier benefits from it.

The shared base is 14px/22px on desktop and 16px/24px for coarse pointers. Avoid tiny
labels, arbitrary font mixtures, or oversized hero typography in operational screens.

## Shared architecture

- Reuse the Blade Hub shell, React HubShell, and shared Filament shell hooks. The shell
  owns the product identity, module label, app switcher, connection treatment, account
  access, and member phone navigation; pages own their operational content.
- App availability comes from existing server authorization/application states.
  Bid and Media Control continue through canonical Hub authorization flows.
- Reuse `hub-appbar`, `hub-page-header`, `hub-btn`, `hub-tag`, `hub-panel`, `hub-tile`, and
  `hub-menu` patterns. Keep one clear heading and one obvious primary action. Use
  contextual HubBack navigation rather than unqualified browser history.
- Reuse Filament configuration, render hooks, existing icons, and the current frontend
  stack. Keep vendor overrides where supported configuration cannot provide required
  accessibility or presentation behavior.

## Layout and interaction

Use the 4px spacing base, 16px phone gutters, 24px tablet gutters, and 32px wide-desktop
gutters. The shared content maximum is 1600px. Use existing 4/6/8/12px radius tokens.
Keep headers compact and preserve useful density at 1280×720.

Admin navigation follows **Operations, Fleet, Logistics, Personnel, Programs,
Communications, System**. All seven sections start closed on each Admin page load and
expand when selected. At wide desktop the sidebar starts expanded; laptop navigation
may use the rail, and tablet/phone uses the drawer. Preserve permissions and visibility.
Important tables need meaningful phone summaries, wrapping, or bounded table scrolling;
the document itself must not overflow horizontally.

Member phone navigation is **Home · Checkout · Forms · Requests · More** where applicable.
Reserve space for it and account for `env(safe-area-inset-bottom)`. Keep operational touch
targets at least 44px, avoid hover-only controls, and keep floating controls clear of forms
and primary actions. Critical Daily and shell controls remain usable at 320px.

Menus need semantic buttons, visible focus, keyboard operation, Escape dismissal, and focus
return. Keep zoom enabled, meaningful icons named, and single-key shortcuts disableable.
Use the shared 2px focus outline with an offset; do not convey status through color alone.

## Status, connection, and motion

Use semantic text, an optional named icon, and the matching `hub-tag` background/border.
Success indicates confirmed completion; warning indicates attention or a pending state;
danger indicates a material failure or destructive action; information explains state.
Reuse existing domain status wording instead of inventing alternate labels.

Daily presents its actual connection, local-save, queue, and sync state. Connected-only
pages say **Requires connection** when offline. Never imply queued work was sent, show
fabricated live status, or advertise offline capability a module does not have. Keep
Daily autosave, retry, idempotency, checklist identity, and submission behavior unchanged.

Use the existing 120/180/240ms motion tokens and restrained enter/exit easing. Respect
`prefers-reduced-motion`; use skeletons for loading and avoid bounces, perpetual decorative
animation, and staged reveals that delay access to operational content.

## Installed application

`public/manifest.json` is the canonical root MBFD Hub install identity. Retain the root
`id`, `start_url`, and scope, and keep legacy manifest compatibility aligned with it.
Daily retains its existing generated `/daily/` scope and service-worker contracts.
All manifests use navy `#102A43`, white `#FFFFFF`, orientation `any`, and separate `any`
and `maskable` icon entries. Maskable assets have an opaque background and keep the
mark inside the central 40%-radius safe circle. Shortcut destinations stay inside their
manifest scope and use existing authorized routes.

Preserve canonical hosts, sessions, install identity, and worker architecture.
Origin unification is separate infrastructure work, not a presentation change.
